The problem with converting JSON to CSV

JSON is a tree. CSV is a grid. There is no lossless mapping between them, so every converter has to make decisions about how to force one shape into the other , and the quality of a converter is entirely about how sensible those decisions are.

Three problems come up every time, and most tools handle at least one of them badly.

Nested objects

A record containing address as an object with city and zip inside it cannot occupy one cell without losing structure. The standard answer, and the one used here, is dotted column names: address.city and address.zip become separate columns. Nesting can go as deep as it likes and the names simply get longer.

The alternative some tools use is dumping the whole object into a single cell as raw JSON. That technically preserves the data but produces a spreadsheet nobody can filter or sort, which defeats the purpose of converting.

Arrays

A field holding three tags has no natural single-cell representation, and the right answer genuinely depends on what you are doing:

  • Joined into one cell is best when you are reading the data , a cell showing founder;engineer is immediately legible.
  • Numbered columns , tags.0, tags.1 , is best when you need to filter or pivot on individual values. The downside is that one record with fifty entries creates fifty columns for everyone.
  • Raw JSON in the cell is best when the data is going into another program that will parse it again.

This tool lets you pick, because there is no single correct choice.

Records that disagree about their fields

Real API responses are ragged. The first record has eight fields, the fortieth has eleven because those users filled in optional profile data. A converter that reads only the first record to build its header silently drops those extra fields, and you will not notice until something downstream is missing.

This tool scans every record before writing the header, so the column set is the union of all keys found anywhere in the data. Records missing a field get an empty cell rather than a shifted row.

Escaping, and why it matters more than it sounds

CSV has one genuinely important rule: a field containing the delimiter, a double quote, or a line break must be wrapped in double quotes, and any double quotes inside it must be doubled.

This is where hand-rolled converters break. A company name like Smith, Jones & Co contains a comma. Written without quoting, it splits into two columns and every field after it shifts left by one , for that row only. Open the result in a spreadsheet and you get data that looks almost right, which is considerably worse than data that looks obviously broken.

The output here is quoted according to RFC 4180, so commas, quotes and newlines inside values survive the round trip.

Getting Excel to open it correctly

Two recurring frustrations, both fixable before you export.

Accented characters turn into gibberish

Excel does not reliably detect UTF-8 encoding on its own, so names with accents or any non-Latin script can arrive mangled. The fix is a byte order mark at the start of the file, which is what the BOM option adds. Leave it on if the file is going into Excel; turn it off if it is going into a script or a database import, where the BOM can show up as stray characters on the first column name.

Everything lands in one column

Excel installations configured for European locales expect semicolons as the delimiter rather than commas. If your file opens as a single column of text, re-export with the semicolon delimiter selected.

What to watch for in the output

  • Long numeric identifiers. Spreadsheets will happily reformat a 16-digit order ID into scientific notation and destroy it. If IDs matter, import rather than double-click, and set that column to text.
  • Leading zeros. A postcode of 01234 becomes 1234 once a spreadsheet decides it is a number. Same fix.
  • Null versus empty. A JSON null and an empty string both become an empty cell, and that distinction cannot be recovered afterward.
  • Column explosion. If numbered array columns produce hundreds of columns, one record in your data has an unusually long array. Switch to joined mode.

Questions

Is my data uploaded anywhere?

No. Parsing and conversion happen in this browser tab. You can confirm it in the Network tab of developer tools , no request carries your JSON.

What JSON structures does it accept?

An array of objects works best. A single object becomes a one-row CSV. An object wrapping an array under a key such as data or results is detected automatically and the inner array is used.

How are nested objects handled?

They flatten into dotted column names, so address.city becomes its own column. Nesting can be any depth. You can turn flattening off to keep objects as raw JSON in a single cell instead.

Why does my CSV look wrong in Excel?

Two usual causes. Accented characters mangled means the encoding was not detected , keep the BOM option on. Everything in one column means your Excel expects semicolons; re-export with the semicolon delimiter.

What if records have different fields?

Every record is scanned before the header is written, so the columns are the union of all keys found. Records missing a field get an empty cell rather than a shifted row.

Can I convert back to JSON afterwards?

Yes , the CSV to JSON tool reads the same dotted column convention, so address.city rebuilds into a nested object. Type information is not perfectly preserved in the round trip, since CSV has no types.
