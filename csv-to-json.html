Why dotted headers exist

Most CSV to JSON converters produce a flat object per row. Every column becomes a top-level key, and that is the end of it. That works until the data you are producing needs to go somewhere that expects structure — an API, a config file, a document database — at which point you are writing a script to reshape the output anyway.

The dotted header convention solves this at the source. A column named address.city becomes a city property inside an address object. Nesting can go as deep as you like: company.billing.address.country creates four levels. Columns sharing a prefix merge into the same object automatically.

Input like this:

  • name, address.city, address.zip

produces a record with name at the top level and an address object holding city and zip. No post-processing required.

Array columns

Ending a header with [] marks the column as a list. The cell is split on semicolons, so a tags[] column containing founder;engineer yields an array of two strings. Semicolons rather than commas, for the obvious reason that commas are already doing a job in a CSV file.

Empty cells in an array column produce an empty array rather than an array containing an empty string, which is nearly always what you want when the result is going into a validator.

Type detection, and when to turn it off

CSV has no types. Everything in the file is text, and a converter has to guess what was intended. With type detection on, this tool converts:

  • Whole numbers and decimals into JSON numbers
  • true, false, yes and no into booleans
  • Empty cells into null

That is right most of the time and wrong in a few specific cases that matter a great deal.

The leading zero problem

A postcode of 01234 is not the number 1234. A phone number starting with a zero, a bank sort code, a product SKU with a fixed-width numeric format — converting any of these to numbers destroys the leading zero permanently.

The parser here deliberately guards against this: a numeric-looking value is only converted if converting and converting back produces exactly the original string. 01234 fails that test and stays a string. So does a 20-digit identifier that would lose precision as a floating point number.

If you want everything as strings regardless, turn type detection off.

Quoted fields, and the bug that produces almost-right data

The CSV specification allows a field to contain the delimiter, quotes, and even line breaks, provided the field is wrapped in double quotes. A quote inside a quoted field is written as two quotes.

Naive parsers that split each line on commas break the moment a value contains a comma. A company name like Smith, Jones and Co becomes two fields, everything after it shifts by one column, and only that one row is affected. The result is a file that looks fine at a glance and is silently wrong in a handful of places, which is far more dangerous than an obvious failure.

This parser walks the file character by character and tracks quote state, so delimiters, quotes and newlines inside quoted fields are handled correctly. It also strips a byte order mark if present, which otherwise attaches itself invisibly to your first column name and causes lookups on that field to fail for reasons nobody can see.

Delimiters beyond the comma

Plenty of files described as CSV are not comma separated. Excel in European locales exports semicolons by default, because the comma is the decimal separator in those regions. Database exports frequently use tabs or pipes.

Automatic detection counts candidate delimiters in the header row and picks the most frequent, which is right nearly all of the time. When it guesses wrong — usually because a header itself contains a comma — set the delimiter manually.

Checking the output before you rely on it

A few things worth glancing at, because they are much cheaper to catch now than downstream:

  • The record count shown above the output should match your row count minus the header. If it is short, some rows were blank or malformed.
  • The first record tells you whether nesting worked. If you see a literal key called "address.city" rather than a nested object, the expand option is switched off.
  • Identifiers that should be strings. Scan for anything that became a number and lost a leading zero.
  • Column count against the source. A mismatch usually means a stray delimiter in a header.

Questions

Is my spreadsheet uploaded anywhere?

No. Parsing happens in this browser tab. That matters more for CSV than for most formats, since exports usually contain customer names, emails and order data.

How do I create nested objects?

Name the column with dots. A header of address.city becomes a city property inside an address object. Any depth works, and columns sharing a prefix merge into the same object.

How do I create arrays?

End the header with [] and separate values in the cell with semicolons. A tags[] column containing founder;engineer becomes an array of two strings.

Will it break my postcodes and IDs?

No. Numeric-looking values are only converted when converting and converting back gives exactly the original text, so leading zeros and long identifiers stay strings. Turn type detection off to keep everything as text.

Does it handle commas inside quoted fields?

Yes. The parser tracks quote state character by character, so delimiters, escaped quotes and line breaks inside quoted fields are handled correctly.

My file uses semicolons — will that work?

Yes. Automatic detection usually catches it, and you can set the delimiter manually if it guesses wrong. Semicolon exports are the default in European Excel locales.

Can I convert JSON back to CSV?

Yes, with the JSON to CSV tool. It uses the same dotted convention, so nested objects flatten back into the same column names.
